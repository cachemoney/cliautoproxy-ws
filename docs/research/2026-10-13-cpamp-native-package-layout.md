# CPAMP native package layout for non-interactive LXC install

Research ticket: cachemoney/cliautoproxy-ws#3 (map: #1)
Date: 2026-10-13. Upstream state verified against: submodule `repositories/CPA-Manager-Plus` @ `9d719fc8` (merge of release v1.14.6), live GitHub release `v1.14.6`, and the docs site (retrieved 2026-10-13).

Question: what exactly ships in seakee/CPA-Manager-Plus release assets, and can the Manager Server be installed non-interactively in a fresh Debian LXC without the guided installer?

**Answer up front: yes.** The release archive is a self-contained static binary with an embedded panel; it runs unprivileged from any directory, reads a plain `config.json` (or env vars), and keeps all state in one data directory. Nothing in the archive or the binary requires the installer, root, Docker, or a TTY. The gaps a community script must fill: no systemd unit ships in the archive (the installer only *writes* one into the install dir and never enables it), no checksum verification in the installer, and the default first-run admin key is printed to logs (script should pre-provision it).

---

## 1. Release assets and naming

Verified live on releases v1.14.2–v1.14.6 (`gh api repos/seakee/CPA-Manager-Plus/releases/...`); naming is generated by `bin/release/package-native.sh` (submodule, lines 33–40, 44, 69–78):

- Pattern: `cpa-manager-plus_<version>_<goos>_<goarch>.tar.gz` (`.zip` for windows), where `<version>` is the release tag **with** the leading `v`.
- Linux: `cpa-manager-plus_v1.14.6_linux_amd64.tar.gz`, `cpa-manager-plus_v1.14.6_linux_arm64.tar.gz`.
- Also published: `checksums.txt`, `management.html` (standalone single-file panel), `release-info.json` (update-channel metadata).
- Download URL shape: `https://github.com/seakee/CPA-Manager-Plus/releases/download/v1.14.6/cpa-manager-plus_v1.14.6_linux_amd64.tar.gz` (constructed exactly this way by `bin/install-cpamp.sh` line 3941).
- `checksums.txt` format: `<sha256>  ./cpa-manager-plus_v1.14.6_linux_amd64.tar.gz` (two-space separator, `./`-prefixed names) — generated by `sha256sum ./* > checksums.txt` in `package-native.sh` lines 82–89. Works with `sha256sum -c checksums.txt` after downloading assets into the cwd. I verified the linux_amd64 archive hash matches (`0490fe02…`).
- Arch mapping (docs: Native Packages → Download): `uname -m` `x86_64 → amd64`, `aarch64|arm64 → arm64`.

## 2. Archive layout

Verified by downloading and extracting the v1.14.6 linux_amd64 tarball:

```
cpa-manager-plus_v1.14.6_linux_amd64/     # single top-level dir named after the package
├── cpa-manager-plus                      # the Manager Server binary (~23 MB)
├── cpa-manager-plusctl                   # nohup+pidfile control script (start/stop/restart/status/logs)
├── README.md / README_CN.md / LICENSE
└── docs/                                 # full docs tree incl. release notes
```

Key properties:

- **Binary is statically linked** (`file`: "ELF 64-bit … statically linked, stripped"). `package-native.sh` line 55 builds with `CGO_ENABLED=0` — no libc/glibc version concerns on a minimal Debian LXC; no runtime dependencies beyond the kernel.
- **The web panel is embedded in the binary.** `package-native.sh` lines 28–31 copy `apps/web/dist/index.html` (as `management.html`), favicon and touch-icon into `apps/manager-server/internal/httpapi/web/` before `go build`, so the binary serves `/management.html` itself. Nothing external to deploy or keep in sync.
- **No config, no systemd unit, no data files ship in the archive.** First run creates them (see §3).
- `cpa-manager-plusctl` is a self-contained background runner (`bin/native/cpa-manager-plusctl.sh`): writes `run/` + `logs/` inside the extracted dir (0700/0600), verifies PID records against process start-time/binary. It is a convenience for bare-metal manual runs, **not** a supervisor; irrelevant once systemd manages the service.

Binary subcommands (from `apps/manager-server/cmd/cpa-manager-plus/main.go` lines 38–102): `--version`/`-v` (prints `buildinfo.Version`, e.g. `v1.14.6`, without touching config/db), `reset-admin-key`, `cleanup-derived`, `compact-usage`, `store-cpa-connection`, `manager-data-snapshot`, `sanitize-runtime-config`; no args → run server.

## 3. Config, data paths, run-as assumptions

From `apps/manager-server/internal/config/config.go`:

- Config file: `$CPA_MANAGER_CONFIG` env, else `config.json` **next to the binary** (`executableConfigPath`, lines 279–285). If missing on server start it is auto-created with `{"httpAddr":"0.0.0.0:18317","dataDir":"./data"}` (lines 260–277).
- **Relative paths in `config.json` resolve against the config file's directory, not the cwd** (`resolveConfigPath`, lines 391–397). So a config at `/opt/cpa-manager-plus/config.json` with `"dataDir": "/var/lib/cpa-manager-plus"` or a relative `../var/lib/...` both work; the upstream installer exploits this with `"dataDir": "../../data"`.
- Data defaults: `dataDir` `./data` next to config (or `/data` when no config file exists at all — a Docker-ism that never fires when a config exists); `usage.sqlite` at `$dataDir/usage.sqlite`; `data.key` at `$dataDir/data.key`; archives under `$dataDir/usage-archives/`.
- Relevant env overrides (env beats config): `HTTP_ADDR` (default `0.0.0.0:18317`), `USAGE_DATA_DIR`, `USAGE_DB_PATH`, `CPA_MANAGER_DATA_KEY_PATH`, `CPA_MANAGER_ADMIN_KEY` / `CPA_MANAGER_ADMIN_KEY_FILE`, `PANEL_PATH`, `USAGE_COLLECTOR_MODE`, `USAGE_BATCH_SIZE`, `USAGE_POLL_INTERVAL_MS`, `USAGE_QUERY_LIMIT`. Legacy CPA creds: `CPA_UPSTREAM_URL`, `CPA_MANAGEMENT_KEY[_FILE]` (the installer actively *unsets* these; connection now lives encrypted in SQLite).
- **Admin key**: env `CPA_MANAGER_ADMIN_KEY` > file from config `adminKeyFile` (default `/run/secrets/cpa_admin_key`, another Docker-ism) > **generated on first start and printed once to stdout/logs** (`cpamp_…` prefix). Recovery: `cpa-manager-plus reset-admin-key [--db-path …] [--admin-key … | --admin-key-file …]`. A script that pre-provisions the key file (0600) gets a deterministic credential with no log-scraping.
- **`data.key` decrypts the CPA Management Key stored in SQLite.** Lose it and the stored CPA connection is unrecoverable (must be re-entered in the panel). It is *the* critical backup artifact together with the SQLite files.
- **Run-as: no root requirement.** The docs' systemd example creates a dedicated system user; the binary needs only write access to its data dir (and config dir if first-run config creation is allowed). No capabilities, no `/proc` writes, no privileged ports (18317 unprivileged). The installer's own unit has no `User=` (runs as root) but nothing requires it.
- Single-instance constraint: the server takes an exclusive process lock on `usage.sqlite` (`main.go` line 115) — exactly one Manager Server per DB/CPA usage queue. systemd `Restart=on-failure` is fine; never run a second copy during upgrades.

## 4. systemd: what ships vs. what the script must author

- **No unit ships in the archive**, and `cpa-manager-plusctl` is not a systemd integration.
- The one-click installer *writes* `<install_dir>/cpa-manager-plus.service` on Linux (`bin/install-cpamp.sh` `write_native_systemd_service`, lines 3854–3925) but **never installs or enables it**: no copy to `/etc/systemd/system`, no `daemon-reload`, no `enable`. It starts the server with `nohup run.sh &` + pidfile (`run_native_install`, lines 4506–4546) and the docs say explicitly: "On Linux it also creates `cpa-manager-plus.service`; copy it into your systemd service directory and enable it according to your host policy" (installer doc, Native Package Mode).
- Installer unit contents (fresh-install variant): `Type=simple`, `Wants/After=network-online.target`, `WorkingDirectory=<runtime dir>`, `ExecStart=<runtime dir>/cpa-manager-plus`, `Restart=on-failure`, `RestartSec=5s`, `WantedBy=multi-user.target`, plus `Environment=` lines emptying legacy `CPA_UPSTREAM_URL`/`CPA_MANAGEMENT_KEY[_FILE]`. No `User=`.
- The docs site's own recommended unit (Native Packages → Linux systemd example) is the better template for a community script — dedicated user, fixed program dir, data outside the program dir:

```ini
[Unit]
Description=CPA Manager Plus Manager Server
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=cpa-manager-plus
Group=cpa-manager-plus
WorkingDirectory=/opt/cpa-manager-plus
ExecStart=/opt/cpa-manager-plus/cpa-manager-plus
Restart=on-failure
RestartSec=3
Environment=HTTP_ADDR=0.0.0.0:18317
Environment=USAGE_DATA_DIR=/var/lib/cpa-manager-plus

[Install]
WantedBy=multi-user.target
```

## 5. What `bin/install-cpamp.sh` does (and what to replicate or skip)

The installer (≈4700 lines) is env-driven and fully non-interactive-capable. Contract (from `require_interactive_tty`, `collect_choices`, `confirm_choices`, and the installer docs page):

```
CPAMP_NON_INTERACTIVE=1 CPAMP_CONFIRM=1 CPAMP_LANG=en-US
CPAMP_INSTALL_MODE=cpamp            # CPAMP-only (stack+native unsupported)
CPAMP_DEPLOY_METHOD=native
CPAMP_INSTALL_DIR=<dir>             # default ~/cpa-manager-plus
CPAMP_PORT=18317                    # default
CPAMP_VERSION=latest|vX.Y.Z         # latest resolves via update-channel/stable-version.txt
CPAMP_CPA_CONNECTION_MODE=setup     # non-interactive default: configure in panel later
# or: =env + CPAMP_CPA_URL + CPAMP_CPA_MANAGEMENT_KEY for offline import
CPAMP_OPERATION=install|upgrade|repair|regenerate   # required if a deployment exists
CPAMP_DRY_RUN=1 / CPAMP_SKIP_EXECUTE=1             # plan-only modes
```

What it does in native mode (`generate_native_files` lines 3927–4009, `run_native_install` 4506ff): detect os/arch (linux/darwin, amd64/arm64 only) → resolve version (`resolve_latest_version` 3728–3749: `curl raw.githubusercontent.com/seakee/CPA-Manager-Plus/update-channel/stable-version.txt`, regex-validated) → `curl -fL` the tag-pinned asset (**no checksum verification**) → `tar -xzf` into `<install_dir>/runtime/<package>/` → generate admin key `cpamp_` + 32 alnum into `secrets/cpamp-admin-key` (0600, openssl/urandom) → write `runtime/<pkg>/config.json` (`httpAddr`, `dataDir: ../../data`, `adminKeyFile: ../../secrets/cpamp-admin-key`, `dataKeyPath: ../../data/data.key`) → write `run.sh` wrapper → write `cpa-manager-plus.service` → optionally `store-cpa-connection` offline import → `nohup run.sh` → poll `/health` → verify admin via `GET /status` w/ Bearer → verify CPA via `POST /v0/management/cpa-connection/validate`.

**A community script can replicate directly:** version resolution (or `check_for_gh_release`'s GitHub latest), tag-pinned asset download, extraction, admin key pre-provision, config.json with explicit paths.
**Can skip:** docker path, interactive confirm/summary, CPA-connection import (panel first-setup handles it — `CPAMP_CPA_CONNECTION_MODE=setup` equivalent), the nohup/pidfile machinery (systemd instead), its snapshot/rollback machinery (replaced by a simple data-dir backup).
**Must add:** authoring + enabling the systemd unit (with service user), checksum verification against `checksums.txt` (upstream installer skips this), and its own data backup on update.

## 6. Update path (detect + upgrade in place, preserving data)

- **Current version:** `cpa-manager-plus --version` prints the tag (e.g. `v1.14.6`) without starting the server or touching config/db. Community-scripts' `check_for_gh_release "<app>" "seakee/CPA-Manager-Plus"` gives the cached-vs-latest gate (latest release tag is the same target the upstream update-channel points to: `stable-version.txt` → `v1.14.6` today; `update-index.json` carries stable/rc/beta pointers).
- **Upgrade procedure** (docs: Upgrade CPA Manager Plus → "Linux systemd With A Fixed Program Directory" — matches the `/opt` + `/var/lib` layout exactly):

```bash
sudo systemctl stop cpa-manager-plus
sudo cp -a /var/lib/cpa-manager-plus "/var/lib/cpa-manager-plus.backup.$(date +%Y%m%d%H%M%S)"
# verify new asset against checksums.txt, then:
sudo cp -a cpa-manager-plus_vX.Y.Z_linux_amd64/. /opt/cpa-manager-plus/
sudo systemctl start cpa-manager-plus
sudo systemctl status cpa-manager-plus
```

- **Data preservation rules** (docs: Before You Upgrade / Data Location):
  - Keep `USAGE_DATA_DIR` outside the program dir so release files never overwrite runtime data.
  - Back up (only while stopped): `usage.sqlite`, `usage.sqlite-wal`, `usage.sqlite-shm`, `data.key`, plus `usage-archives/` if used. Never copy just `usage.sqlite` without WAL/SHM.
  - Schema migrations run automatically at startup — never run SQL manually, never run two instances against one DB.
  - Losing `data.key` means re-entering the CPA Management Key in the panel; usage history survives.
- **Verify:** `curl -f http://127.0.0.1:18317/health`, then authed `GET /status` (Bearer admin key) — panel and server report the target version; `/status.databaseMaintenance.required` should settle to `false` (deferred index work may need a one-off stopped-service `cleanup-derived` on large historic datasets).
- Community-scripts shape (mirroring `ct/cliproxyapi.sh` in community-scripts/ProxmoxVE):

```bash
check_for_gh_release "cpamanagerplus" "seakee/CPA-Manager-Plus" || exit 0
systemctl stop cpa-manager-plus
create_backup /opt/cpa-manager-plus/config.json     # config lives in program dir
# /var/lib/cpa-manager-plus is untouched by the deploy
fetch_and_deploy_gh_release "cpamanagerplus" "seakee/CPA-Manager-Plus" "prebuild" "latest" \
  "/opt/cpa-manager-plus" "cpa-manager-plus_*_linux_$(arch_resolve "amd64" "aarch64").tar.gz"
restore_backup                                       # re-apply config.json over the new release files
systemctl start cpa-manager-plus
```

  Note the one wrinkle: the archive extracts a **top-level versioned directory** (`cpa-manager-plus_vX.Y.Z_linux_amd64/`); the deploy helper's unpacked-archive handling must flatten that into the target dir (as `cliproxyapi`'s equally versioned-dir archives already do).

## 7. LXC-hostility inventory

| Concern | Finding | Source |
|---|---|---|
| Interactive-only installer | No — full `CPAMP_NON_INTERACTIVE=1 CPAMP_CONFIRM=1` env contract; irrelevant anyway if the script installs the archive directly | install-cpamp.sh 347–359, 2668–2676; installer docs |
| Hardcoded paths | No hardcoded install paths in the binary. Docker-ism defaults (`/data`, `/run/secrets/cpa_admin_key`) only apply with **no** config file/env; avoided by shipping a config.json or env vars | config.go 18–20, 115–155 |
| Root assumption | No; docs' own unit uses a dedicated system user, binary needs only data-dir writes | docs Native Packages systemd example |
| Unpinned download URLs | Assets are tag-pinned; installer's `latest` resolves through a validated `stable-version.txt` | install-cpamp.sh 3728–3749, 3941 |
| No shipped systemd unit | **Gap** — script must author and enable the unit (installer never does; it nohups) | §4 above |
| No checksum verification by installer | **Gap** — but `checksums.txt` is published; script should verify | install-cpamp.sh 3982–3995; package-native.sh 82–89 |
| Admin key printed to logs once by default | **Gap-ish** — pre-provision `CPA_MANAGER_ADMIN_KEY_FILE`/env or config `adminKeyFile` for determinism | docs Native Packages "Run Manually" |
| Single-instance/process lock | Operational constraint — don't script parallel starts; stop before backup/upgrade | main.go 115; update docs |
| Static binary, no deps | Friendly — CGO_ENABLED=0, works in minimal Debian LXC | package-native.sh 55; `file` on v1.14.6 |
